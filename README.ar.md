# Balloc.js

## مُخصِّص ذاكرة بأسلوب التخصيص المتزايد (Bump Allocation) لـ JavaScript

**`Balloc`** مُخصِّص ذاكرة تزايدي قائم على أسلوب التخصيص المتزايد (bump allocation). يدير كتل بيانات متجاورة ويعرّفها باستخدام مقابض رقمية مدمجة.

## الدافع

افتقر نظام JavaScript/Node.js البيئي تاريخيًا إلى بنية تحتية منخفضة المستوى لمعالجة البيانات الضخمة بكفاءة، مثل تحليل ملفات CSV والسجلات والسلاسل الزمنية الكبيرة وتحريرها وفهرستها باستمرار. وتعتمد الغالبية العظمى من مكتبات البيانات المتاحة على نماذج بسيطة قائمة على رسوم بيانية للمراجع، وعلى التخصيص الديناميكي لكائنات حرفية (`new Node()`). وتفرض هذه الأساليب قيودًا كبيرة، منها:

* **عبء الذاكرة المؤقتة وجامع القمامة (GC):** يؤدي إنشاء ملايين الكائنات الفردية إلى تضخّم رسم المراجع في V8، ما يسبب توقفات غير متوقعة لجامع القمامة.
* **غياب التحكم في تخطيط الذاكرة (AoS مقابل SoA):** تتجاهل المكتبات تنظيم البيانات وفق أسلوبي Array of Structures (AoS) أو Structure of Arrays (SoA)، ما يؤدي إلى تجزئة كبيرة واستفادة ضعيفة من ذاكرة التخزين المؤقت للمعالج L1/L2/L3.
* **غياب البُنى الأولية اللازمة لإنشاء محركات تخزين متقدمة:** يتطلب إنشاء محركات مثل Log-Structured Merge Trees مناطق كتابة قابلة للتعديل ذات معدل نقل مرتفع جدًا، تتبعها عملية ضغط إلى صيغة غير قابلة للتعديل؛ وهو أمر يصعب تحقيقه باستخدام تجريدات JavaScript التقليدية.

أُنشئ Balloc لسد هذه الفجوة الهندسية. وقد صُمم ليكون محركًا أساسيًا منخفض التجريد لتخصيص الذاكرة وإدارة مناطق الذاكرة الديناميكية (arenas). ومن خلال إتاحة التحكم الصريح في تخطيط الذاكرة المتجاورة عبر TypedArrays، يوفر Balloc الأساس المادي اللازم لبناء هياكل بيانات بمستوى الإنتاج الصناعي في منظومة JavaScript، مثل LSM Trees وMemTables وQuotient Filters ومعالجات البيانات الضخمة. ويهدف إلى مضاهاة كفاءة الحلول الأصلية المكتوبة بـ C++ أو Rust أو Go وقابليتها للتنبؤ.

## التصميم

صُمم **`Balloc`**، بوصفه محركًا منخفض التجريد لتخصيص الذاكرة وإدارة مناطق الذاكرة الديناميكية، ليتكامل مع بيئة تشغيل JavaScript، لا لينافس هياكل البيانات عالية المستوى المدمجة فيها مثل `Object` و`Map` و`Array`. بل يعمل في الطبقة الأدنى مباشرةً، موفرًا **إدارةً حتمية وعالية الأداء للذاكرة المتجاورة** من دون تحميل جامع القمامة في البيئة عبئًا زائدًا.

يجمع المُخصِّص بين ثلاث آليات:

```text
                  ┌─────────────────┐
                  │     Balloc      │
                  └────────┬────────┘
                           │
          ┌────────────────┼────────────────┐
          │                │                │
          ▼                ▼                ▼
   التخصيص المتزايد     إعادة الاستخدام      ضغط الذاكرة
          │                │                │
     تخصيص تسلسلي سريع   إعادة استخدام      ReBump / gc()
                         المناطق المحررة
```

* يخصص مُخصِّص bump الذاكرة تسلسليًا في `dataBus`.
* تتيح آلية إعادة الاستخدام الاستفادة مجددًا من المناطق المحررة سابقًا عندما تتوافق سعتها مع طلب التخصيص الجديد.
* تنفّذ `gc()` عملية ضغط صريحة عندما يحتوي الـheap على مناطق حرة مجزأة.

يوفر ذلك نموذجًا بسيطًا للذاكرة مع الحفاظ على تحكم صريح في السعة والإشغال وإعادة الاستخدام والضغط، إذ يفصل Balloc بين كتلة البيانات وكتلة البيانات الوصفية.

```text
                    Balloc
                       │
             ┌─────────┴─────────┐
             │                   │
          dataBus            controlBus
             │                   │
          المحتوى                الرؤوس
```

* يحتوي `dataBus` على كتل البيانات.
* يحتوي `controlBus` على مجموعة من الرؤوس ثابتة الحجم التي تصف كتل البيانات.

تُعرَّف كل كتلة خارجيًا بواسطة مقبض منطقي من 43 بتًا:

```text
┌────────────────────────┬──────────────────────────────┐
│ الجيل — 11 بتًا         │ عنوان الرأس — 32 بتًا        │
└────────────────────────┴──────────────────────────────┘
```

لا يحتوي المقبض بحد ذاته على عنوان كتلة البيانات مباشرةً، بل يحدد رأس الكتلة، الذي يحتوي بدوره على عنوان البيانات وسعتها وحجمها المشغول.

يُستخدم رقم الجيل في آلية التحقق من Cookie الخاصة بالمُخصِّص للكشف عن المقابض غير الصالحة أو القديمة أو التالفة.

## الاستخدام الأساسي

ESM:

```js
import Balloc from "Balloc";

const memory = new Balloc();

const handler = memory.alloc(100);

memory.push(handler, 10);
memory.push(handler, 20);
memory.push(handler, 30);

console.log(memory.length(handler));
console.log(memory.occupied(handler));

console.log(memory.pop(handler));
console.log(memory.pop(handler));

memory.free(handler);
```

## البدء

صيغة المُنشئ:

```js
new Balloc(size, bucketSize, metadataSize)
```

| المعامل | النوع | القيمة الافتراضية | الوصف |
|---|---|---:|---|
| `size` | `number` | `65535` | السعة الابتدائية لـ`dataBus` بالبايت |
| `bucketSize` | `BucketType` | `32u` | حجم العنصر بالبت |
| `metadataSize` | `number` | `1024` | السعة الابتدائية لـ`controlBus` بالبايت |

مثال:

```js
const memory = new Balloc();
```

لاستخدام عناصر من أعداد صحيحة غير موقعة بعرض 32 بتًا:

```js
const memory = new Balloc(65535, "32u");
```

يجب أن تكون `size` عددًا صحيحًا ضمن النطاق `[2, 0x80000000]`.

يجب أن تكون `bucketSize` قيمةً من نوع `BucketType`، أي سلسلة بالصيغة `[حجم البتات][نوع البيانات]`. القيم المقبولة هي:

| عدد صحيح موقّع | عدد صحيح غير موقّع | عدد عشري عائم |
|---|---|---|
| `8i` | `8u` |  |
| `16i` | `16u` |  |
| `32i` | `32u` | `32f` |
| `64i` | `64u` | `64f` |

لا يضمن Balloc دعم نوع الفاصلة العائمة نصف الدقة (`16f`)، نظرًا إلى حداثة إضافته إلى مواصفات JavaScript وبيئات التشغيل، واستمرار مرحلة ترسيخ دعمه. وحتى مع وجود هذا النوع في المكتبة، قد لا يكون توفره مضمونًا في مشروعك.

يجب أن تكون `metadataSize` عددًا صحيحًا ضمن النطاق `[16, 0x80000000]`.

يُقرَّب حجم تخصيص الكتلة إلى أصغر قوة للعدد 2 قادرة على استيعاب عدد العناصر المطلوب.

على سبيل المثال:

```js
const handler = memory.alloc(100);
```

لا يعني ذلك بالضرورة إنشاء كتلة تحتوي فعليًا على 100 خانة بالضبط؛ إذ يحجز المُخصِّص سعةً تمثل قوةً للعدد 2.

تصوريًا:

```text
العناصر المطلوبة: 100
السعة:             128
```

تختلف السعة المادية عن الإشغال المنطقي:

```text
length(handler)     → السعة المادية
occupied(handler)  → عدد العناصر المشغولة
byteSize(handler)  → عدد البايتات المحجوزة ماديًا
```

يتيح هذا التمييز أن تحتوي الكتلة على عناصر مشغولة أقل من سعتها المادية.

## واجهة API

دورة الحياة الأساسية للكتلة:

```text
alloc()
   │
   ├── الوصول / التعديل
   │
   ├── realloc()
   │
   └── free()
          │
          └── إعادة الاستخدام
```

يوفر Balloc عدة نماذج للتعامل مع بيانات الكتلة:

* المكدس (Stack)
* الطابور (Queue)
* المصفوفة / الوصول العشوائي

### إدارة دورة الحياة

| API | الوصف |
|---|---|
| `alloc()` | تخصيص كتلة |
| `realloc()` | زيادة سعة الكتلة |
| `free()` | تحرير كتلة |
| `gc()` | ضغط كومة البيانات |

| API | الوصف |
|---|---|

| API | الوصف |
|---|---|

### الدوال الداخلية

تمثل هذه الدوال حالة خاصة من واجهة API، وتُستخدم أساسًا داخل المُخصِّص نفسه. لا يُوصى عادةً باستعمالها في الشيفرة اليومية، إذ قد تُحدث آثارًا جانبية غير موثقة. وهي مخصصة لتوسيع المكتبة أو تعديلها، ويتطلب استخدامها فهمًا كاملًا للشيفرة المصدرية لـBalloc.

```text
إعادة التدوير
├── recyclePush()
└── recyclePop()

التوسعة
├── grow()
└── headerGrow()

التحقق / البيانات الوصفية
├── extractMetadata()
└── bakeCookie()
```

تضيف `recyclePush()` كتلةً محررة إلى قائمة إعادة الاستخدام.

تزيل `recyclePop()` كتلةً محررة من قائمة إعادة الاستخدام وتعيدها.

توسّع `grow()` الـ`dataBus` عندما تعجز المنطقة الحالية عن تلبية طلبات التخصيص اللاحقة.

توسّع `headerGrow()` الـ`controlBus` عند الحاجة إلى رؤوس إضافية.

تفك `extractMetadata()` ترميز المقبض وتتحقق من صلاحيته، ثم تستخرج البيانات الوصفية المرتبطة به.

تحسب `bakeCookie()` قيمة Cookie للتحقق، وتُستخدم في آلية التحقق من المقابض.
